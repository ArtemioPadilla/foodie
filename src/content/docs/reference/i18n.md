description: English, Spanish and French by route — typed dictionaries, t() with interpolation and plurals, trilingual catalog text, and the lang-by-prop rule for islands.
---

Foodie ships in English (`/`), Spanish (`/es/`) and French (`/fr/`). Each
language is a set of static routes; there is no runtime language switch inside
a page and no i18next. The language switcher is an ordinary link to the same
page in another locale.

## Two kinds of text

| Kind | Where it lives | How to pick it |
|---|---|---|
| UI strings (buttons, headings, messages) | `src/i18n/en.ts`, `es.ts`, `fr.ts` | `t(lang, 'planner.title')` |
| Catalog text (recipe names, steps, ingredient descriptions, categories) | `public/data/*.json` as `{ en, es, fr }` (`MultiLangTextSchema`) | `getTranslated(recipe.name, lang)` |

`en.ts` defines the `Dictionary` type (`typeof en`); `es.ts` and `fr.ts` are
typed against it, so a missing key is a TypeScript error, not a blank on
screen. The catalog check fails when a catalog string is blank in any of the
three languages.

## Helpers (`src/i18n`)

| Helper | Use | Example |
|---|---|---|
| `t(lang, key, params?)` | UI string by dot path, `{{x}}` interpolation, `_plural` keys | `t(lang, 'common.reviewCount', { count: 3 })` → `3 reviews` |
| `getTranslated(text, lang)` | A `MultiLangText`, with English fallback | `getTranslated(recipe.name, lang)` |
| `detectLocale(pathname)` | The locale of an Astro page from its URL | `detectLocale(Astro.url.pathname)` |
| `localizedRoute(path, lang)` | Locale-aware href (always with a trailing slash) | `withBase(localizedRoute('/recipes/', lang))` |
| `hreflangAlternates(path, origin, base)` | `<link rel="alternate">` per locale for SEO | used by every page wrapper |
| `LOCALES`, `DEFAULT_LOCALE`, `Locale` | Iteration and typing | `LOCALES.map(…)` |

## The rule: `lang` is a prop

Islands hydrate in the browser, outside the Astro request, so they cannot know
the page's locale by themselves. The page passes it:

```astro
---
import RecipeBrowser from '@/components/islands/RecipeBrowser';
import { detectLocale } from '@/i18n';
const lang = detectLocale(Astro.url.pathname);
---
<RecipeBrowser client:load lang={lang} />
```

Never read `navigator.language` or `document.documentElement.lang` during
render: the HTML was generated for one locale, and a different value in the
browser would hydrate a mismatched tree. Values that genuinely depend on the
browser (such as the default unit system) are read in an effect, rendering a
locale-neutral fallback first. Stores and pure functions take `lang` as an
argument; they never import a "current language".

## Adding a string

1. Add the key to `src/i18n/en.ts` in its group (`recipe.*`, `planner.*`, …).
2. `npm run type-check` fails until `es.ts` and `fr.ts` have it too.
3. Keep the same `{{placeholders}}` in the three languages. For counts, add a
   `<key>_plural` sibling.

`src/tests/i18n.test.ts` checks key parity, empty values, duplicate keys,
placeholder sets and plural pairs; the e2e suite fails if a raw key such as
`planner.title` ever reaches the page.

## Adding a page in three languages

Create the EN page and the `es/` and `fr/` wrappers around one shared body in
`src/components/pages/`. `src/tests/route-parity.test.ts` checks that every
localised page has an English twin and that Spanish and French cover the same
pages.

These docs are the exception: they are written in English only, and `/es/docs/`
and `/fr/docs/` are short landing pages that point here. Their English-only
routes are listed in `EN_ONLY_ALLOWLIST` in the route-parity test.

## First visit and v1 visitors

On the English landing page only, an inline script in `BaseLayout` runs once
per browser: when no explicit choice is stored in `foodie:locale`, it takes
v1's `i18nextLng` (or, failing that, the browser language), stores it, and sends
a Spanish or French visitor to `/es/` or `/fr/`. It runs before any island, so
it does not break the lang-by-prop rule, and it never overrides a choice made
with the language switcher.
